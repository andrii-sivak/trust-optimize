# Currency / reality-check review — spine amendment for #30 (AD-7, AD-9, AD-10, Deferred)

- Reviewed: uncommitted diff of `ARCHITECTURE-SPINE.md` (2026-11-17), plus the unchanged AD-5 text the amendment leans on.
- Sources checked:
  - bundled `vendor/woocommerce/action-scheduler` **3.9.3** (paths below are relative to it);
  - upstream `woocommerce/action-scheduler` tags **4.0.0**, **4.2.0** (latest stable) and **trunk** (4.3.0, unreleased), fetched raw from GitHub on 2026-11-17;
  - https://actionscheduler.org/api/ (documented API);
  - https://developer.woocommerce.com/2026/06/17/changes-to-action-scheduler/ (4.0.0 changes; WooCommerce 11.0 ships AS 4.0.0, so a newer copy wins via `ActionScheduler_Versions` on sites with current WooCommerce).

## Verdict

The AS facts the amendment relies on hold in 3.9.3 and 4.x, with one exception: what `modified` means for `failed` actions changed in 4.0.0. One consequence of the AS cleanup was missed. AS itself marks a *live* in-progress action as `failed` after about 300 s. So the AD-10 absence test does not protect a live conversion that runs longer than 900 s. Two smaller API caveats should go into the #30 spec.

## Findings

### F1 — Medium/High: AS fails a live in-progress action after about 300 s, so the AD-10 absence test does not protect long live conversions
- `mark_failures()` (3.9.3 `QueueCleaner.php:206-226`; trunk `:354-376`) marks **every** `in-progress` action whose `last_attempt_gmt` is older than 10 × time limit (300 s) as `failed`. It assumes the action died, and it does not check whether the process is alive. `run()` calls it on every WP-Cron/system-cron/WP-CLI tick **before** the concurrency check, so it runs even while our action holds the only claim.
- Result: a conversion that legitimately runs longer than about 300 s plus the next cron tick has no `pending`/`in-progress` action any more. Once the attachment has been `processing` for 900 s, the AD-10 "confirmed death" fires on a live worker. The AD-10 bullet "While such an action exists, nothing takes the attachment over by age" is true but gives no protection here. After 300 s the action no longer exists, so the only protection is the "late worker" rule (conditional closing writes).
- When it happens: workers with no PHP time limit, that is WP-CLI `wp action-scheduler run`, system cron calling `wp cron event run`, or hosts with a high `max_execution_time`. In PHP-FPM with typical limits the process is killed first, so it really is dead.
- Effect: the AD-10 "Prevents: a live long conversion taken over by age" is met only for conversions shorter than 900 s. Recommend that AD-10 say so: "the absence test protects attempts up to `STALE_CLAIM_SECONDS`; beyond that, AS's own failure period has already removed the action, and the late-worker rule is the only protection". The #30 spec should also test with a fixture whose action AS marked `failed` while the worker is still running.

### F2 — Medium: `modified` on `failed` actions is the *start* time in 3.9.3 and the *failure* time in 4.x
- 3.9.3 `mark_failure()` (`DBStore.php:1215-1236`) does not touch `last_attempt_gmt`. 4.0.0+ sets it (4.0.0 `DBStore.php:1242-1244`, PR #1310).
- Effect on the AD-9 "No progress" signal, if it counts `failed` as "finished":
  - 3.9.3: a failure is dated by when the action started, so a failure that took longer than 900 s does not count, and every timeout failure from `mark_failures` falls outside the window. Mostly harmless.
  - 4.x: a timeout failure written by AS's cleanup counts as "finished within the threshold". That is not progress: it means a worker died. So a dead worker *suppresses* the "No progress" signal for up to 900 s.
- Recommend that the #30 spec define "finished" as `status = complete` only, or `complete` plus `failed` with the version caveat written down. Restricting to `hook = trust_optimize_process` (the conversion hook) would also stop recurring Maintenance and producer wait cycles from counting as progress. The spine may stay as it is if the spec pins this down; the Deferred list could name it.

### F3 — Low: an absence answer from AS fails open
- `as_has_scheduled_action()` returns `false` when the data store is not initialized (`functions.php:400-402` → `ActionScheduler::is_initialized()`, `abstracts/ActionScheduler.php:270-281`). It also returns `false` when the query fails: a DB error gives `get_col()` = `[]`, so `query_action()` returns `null` (`abstracts/ActionScheduler_Store.php:128-136`, `DBStore.php:646`). A missing AS table on a network site (AD-16 mentions this case) is one way to hit it.
- AD-10 turns "no action" into a **confirmed death**, which costs an attempt and can end in `failed`/`max_attempts`. The spec should require a positive answer: AS functions exist, `ActionScheduler::is_initialized()` is true, and AS tables exist on that site. Anything else means "unknown, do nothing". The existing `function_exists()` guards cover only the first.

### F4 — Low (trunk only, unreleased 4.3.0): `as_has_scheduled_action()` with a group is two non-atomic queries
- trunk `functions.php:418-420` queries `in-progress` first, then `pending`. If an action moves from pending to in-progress between the two (`log_execution`), both miss and the function returns `false`.
- Under AD-10 the attachment must also be `processing` for more than 900 s, so a false confirmed death needs an unlikely overlap. Still, the "pending OR in-progress" claim holds only per query, not as a snapshot. Record it with the AS upgrade (#1). A safer read on 4.3+ is one `as_get_scheduled_actions()` call with `status => [pending, in-progress]`, `per_page => 1`, `orderby => 'none'`, which stays a single statement.

### F5 — Info: notes for the #30 spec when it writes the queries
- Never-claimed pending actions have `last_attempt_gmt = '0000-00-00 00:00:00'` (`classes/schema/ActionScheduler_StoreSchema.php:14`, `:72`). Any `modified <= cutoff` query without `claimed => true` matches every fresh pending action. The "Stuck claim" definition already requires claimed or in-progress, so keep that.
- Unclaiming (`reset_timeouts`, `release_claim`) does not change `last_attempt_gmt`, so a pending action released from a claim still carries its claim time.
- `per_page` defaults to 5 and `orderby` to `date`. Set `per_page => 1, orderby => 'none'` (the pattern in `includes/health/SiteHealth.php:76-86`).
- `status` accepts an array in both versions (`(array) $query['status']`), although the docblock lists single values only.
- The "Stuck claim" signal is group-scoped, while the async-runner block is global (F-table row 5). A dead claim from WooCommerce or another plugin blocks our work but shows only as "No progress". The two signals complement each other, so the notice text should not say "a TrustOptimize task is stuck" when only "No progress" fires.
- The 900 s threshold gives three times AS's default 300 s cleanup window, so the margin is sound as long as nobody raises the AS time-limit or timeout filters. A site that raises `action_scheduler_queue_runner_time_limit` above 90 s gets "Stuck claim" warnings on claims AS still considers alive. That is acceptable for a diagnostic, but worth one sentence in the notice wording or the spec.
