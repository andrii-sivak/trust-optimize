topic: Images with unknown dimensions bypass pixel and memory limits (#10)
updated: 2026-11-20T14:03
---

- (direction) Scope is issue #10 only. #32 (memory coefficients) and #26 (pace and the AD-11 resource gate) stay deferred. No new memory formula, no adaptive limits, no per-variant park/defer gate.
- (note) ImageLimits::skip_reason multiplies the two integers and returns null when the product is <= 0, so the pixel filter and the memory share are never applied. Callers pass (int)(metadata width ?? 0) and (int)(metadata height ?? 0).
- (note) Production callers of skip_reason are only VariantPlanner::eligible_source and Inventory::inspect. Both use the attached file's metadata, not each size. SettingsFormTest calls skip_reason directly with positive numbers.
- (note) Original dimensions come from wp_get_attachment_metadata width/height, which WordPress sets from wp_getimagesize in wp_create_image_subsizes. They are absent when metadata was never generated, generation returned an empty array, or the keys are missing, zero, negative, or non-numeric. The attached file may be the -scaled file; original_image is the pre-scale upload and is not what the converter opens.
- (note) Size dimensions come from metadata sizes[*] width/height and are copied onto variant rows by desired_variants. ImageConverter never passes them to ImageLimits. It fully decodes each size file via wp_get_image_editor, which calls load().
- (note) Every enqueue (upload metadata, bulk producer) goes through ConversionQueue::plan_and_enqueue, which plans first. REST and WP-CLI sync call AttachmentProcessor::sync, which also plans first. AttachmentProcessor::run, used by the queue worker, does not plan again and converts pending rows directly.
- (note) A planner skip returns existing variant rows for deletion, same as too_large, missing_file, and unsupported_mime. Inventory::inspect counts any non-null skip_reason as oversized_attachments and must not open an editor.
- (note) wp_getimagesize is getimagesize plus header fallbacks. Its HEIC branch calls wp_get_image_editor. JPEG and PNG do not. On trust-optimize-tools php8.0 and php8.5, a 17-byte SOF0 JPEG (SOI + SOF0 + EOI) reports 12000x12000 and 3000x3000. Garbage bytes return false. exif_imagetype is 2 for the SOF file and false for garbage.
- (decision) A dimension counts only when that side is an integer >= 1. Missing, zero, negative, and non-numeric sides are not a size. The product of two negatives must not pass the guard.
- (decision) When both metadata sides are established, skip_reason uses those integers and does not read the file. When they are not, read the attached file's header and then run the same formula. Never read original_image.
- (decision) Header read is jpeg/png only. wp_get_image_mime must be image/jpeg or image/png, then wp_getimagesize. Any other type, a false result, or a non-positive side is unknown_dimensions. Do not call wp_getimagesize otherwise, because the HEIC branch opens an editor.
- (decision) If the header yields positive dimensions, the existing outcomes stay too_large and insufficient_memory. If it does not, the attachment is skipped with unknown_dimensions and no editor is opened.
- (decision) skip_reason stays a pure function of two integers. Non-positive inputs return unknown_dimensions, never null. The header read is one helper used by eligible_source and Inventory::inspect only.
- (decision) Inventory counts too_large and insufficient_memory, including those found from a header, as oversized_attachments. unknown_dimensions does not increment that counter and adds no snapshot key.
- (decision) Do not write attachment metadata, do not modify original or size files, and do not add a second check inside ImageConverter. The worker keeps trusting rows planning already queued.
- (constraint) The pixel filter trust_optimize_max_pixels, DEFAULT_MAX_PIXELS, BYTES_PER_PIXEL, MEMORY_SHARE, and the memory_limit comparison are unchanged. AD-11 is not amended.
- (constraint) No schema change, no new hook, setting, REST route, or WP-CLI parameter. CHANGELOG.md gains one Unreleased bullet. readme.txt FAQ 'Why was an image not converted?' names unknown_dimensions. Comments do not cite the issue or the spec.
- (constraint) Regression tests live in ImageGuardTest and InventoryTest. Build the oversized fixture by uploading a real small JPEG, then replacing the attached file with the 17-byte SOF JPEG and clearing dimensions. Never run create_upload_object on that SOF file. Assert an editor load() does not run. plan_and_enqueue must not schedule ConversionQueue::HOOK_PROCESS for a skipped attachment.
- (capability) CAP-1 An attachment whose metadata has no positive dimensions is still subject to the pixel and memory limits when the attached file header reports dimensions. Success: cleared metadata plus a 12000x12000 header skips with too_large; negative metadata plus that header also skips with too_large; cleared metadata plus a 3000x3000 header under the existing tight memory_limit skips with insufficient_memory. No editor load. Source bytes and attachment metadata unchanged. plan_and_enqueue schedules no process action.
- (capability) CAP-2 An attachment whose dimensions cannot be established is skipped with reason unknown_dimensions and is not decoded. Success: a non-image file stored as image/jpeg with no positive metadata dimensions is skipped with unknown_dimensions, state skipped, no editor load, file bytes unchanged.
- (capability) CAP-3 A JPEG or PNG that is within the limits is still converted when metadata dimensions are missing but the header has them. Success: test-image.jpg with width and height removed converts successfully and its bytes stay unchanged.
- (capability) CAP-4 Library inventory uses the same dimension decision as planning and still does not open an image editor. Success: the 12000 header with empty metadata counts as one oversized attachment; the non-image file does not; an editor load does not run.
- (question) Should this change also refuse each intermediate size file whose own width and height are not positive, or is guarding the attached file enough? Recommended: attached file only. Size dimensions never enter ImageLimits today, and the converter decodes each size file only after the attached file has passed. Closing a size with missing dimensions is a per-file gate and is the start of AD-11.
- (question) Should positive metadata that is smaller than the file header be distrusted? Recommended: no. The header is read only when metadata does not give two positive integers. A lying smaller metadata still bypasses both limits. That is a different bug from unknown dimensions.
- (assumption) REST POST /image/{id}/sync, wp trust-optimize sync-attachment, and sync --now all call AttachmentProcessor::sync, so they follow the planner check without their own tests.
- (assumption) PHP 8.5 getimagesize matches the 8.0 result on the same 17-byte fixture. Neither call allocates a 12000x12000 bitmap.
