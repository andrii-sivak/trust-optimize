topic: GH-9 stale bulk mutex reclaim can delete a new owner's lock
updated: 2026-11-20T11:52

- (note) Issue #9: acquire_mutex reads a stale holder and deletes trust_optimize_bulk_active by option_name only, so two creates can each delete and insert and both leave a job. Proposal: DELETE WHERE option_name and option_value equal the observed holder, then retry the insert once. Acceptance: an integration test that interleaves two create() calls after a stale mutex gets exactly one job.
- (direction) User: confirm the race in current code, audit every mutex capture, write and release, ship the minimal fix so a request cannot delete a new owner's lock, add a reproducible race test plus normal start and release checks, do not rebuild the queue or add unrelated behavior. Spec first; bmad-build only after agreement. No push and no GitHub changes.
- (note) Express distill: issue #9, the mutex methods, and the user constraints are enough. No field-by-field elicitation.
- (note) Code at main 5c72440, branch fix/gh-9-stale-bulk-mutex. The mutex is only BulkJobRepository::ACTIVE_OPTION. insert_mutex is INSERT IGNORE of time(). write_mutex updates option_value by option_name. release_mutex deletes by option_name. acquire_mutex calls that delete when the holder is a timestamp older than MUTEX_STALE_SECONDS (60) or a job id that is not active. create() calls it when the job INSERT fails. finish() reads the value and, when it equals the job id, calls the same delete. pause, mark_running and get_active_job do not write the option. uninstall.php deletes every trust_optimize_* option by name while removing the plugin.
- (decision) The two-create race is real. Both acquires observe the same stale value, both delete by name, and the later delete removes the earlier request's new row. Both inserts then succeed and both create() calls insert a job.
- (decision) finish() has the same hole. After its status CAS the job is no longer active, so a concurrent create() treats that job id as stale, installs a new row, and finish()'s name-only delete removes it.
- (decision) create()'s failure release has the same hole once its timestamp has been replaced. It must delete the timestamp that call inserted, not the value now stored, and it must not re-read the option to choose the value.
- (decision) Every BulkJobRepository delete of the mutex matches option_name and the holder string this call observed or wrote. acquire_mutex then calls insert_mutex once. No retry loop, no new hook, no queue change.
- (decision) write_mutex stays an update by option_name only unless the owner pulls it in. A job INSERT slower than 60s can still store this call's job id over a new owner's value. That is a write, not a delete.
- (decision) AD-6 is not amended. The conditional delete is how the existing one-active-job rule holds under this race. The mutex stays an option row, not a job-status CAS.
- (capability) CAP-1 intent: two requests that both find the same stale bulk mutex end with one active job, and the loser does not remove the winner's lock. success: one interleaved pair of create() calls after a planted stale mutex returns a single job, one active job row, and an option value equal to that job id. The same interleaving on a name-only delete returns two jobs.
- (capability) CAP-2 intent: a request releasing the library removes the mutex only while the stored value is still the one that request holds. success: finishing a job whose mutex was replaced leaves the replacement; a failed job INSERT whose mutex was replaced leaves the replacement and returns false; a failed job INSERT that still holds its own timestamp removes the option.
- (capability) CAP-3 intent: an uncontended start still records the new job id, and cancel or complete still clears it so the next start can take the library. success: create then cancel then create, and create then complete, show the option matching the live job and absent after finish. test_a_second_job_cannot_be_created_while_one_is_active and test_a_mutex_left_behind_by_a_crashed_request_is_taken_over stay green with their current assertions.
- (constraint) A BulkJobRepository delete of trust_optimize_bulk_active matches both option_name and the holder string this call observed or wrote. Name-only delete from that class is gone. delete_option cannot express the predicate, so this path stays on wpdb->delete.
- (constraint) Stale detection is unchanged: a timestamp older than MUTEX_STALE_SECONDS, or a job id whose job is outside JobStatus::active(). A fresh timestamp and an active job still refuse the second create. get_active_job stays a read.
- (constraint) create()'s failure path deletes the timestamp captured for that insert. finish() deletes the string form of the finished job id and does not read the option first.
- (constraint) New tests go in tests/Integration/BulkProducerTest.php beside the existing mutex tests. The race test uses the suite's query filter: the second create() runs once when the first delete is about to execute, then that delete runs. No production hook and no second process.
- (constraint) CHANGELOG.md gains one Unreleased bullet. readme.txt, public hooks, settings, REST, WP-CLI and the schema do not change. Comments on the mutex functions describe the conditional delete in their own words and do not name the issue.
- (assumption) Job ids stay below 1000000000, so the existing comparison still separates a timestamp from a job id. A new owner's value differs from the value the losing call observed: the new owner writes a new time() or a new job id, and the same unix second is written only after the old row is gone.
- (assumption) Interleaving through the query filter inside one PHP request reproduces the two-create race. The suite already uses that filter to intercept queries.

- (constraint) deferred-work.md gains one entry for the slow create. Consequences: Ja and Jb are both active, the option names Ja, get_active_job can return Jb, finish(Jb) does not clear the option, finish(Ja) clears it while Jb is still active, and create refuses a third job only because an active row exists.
