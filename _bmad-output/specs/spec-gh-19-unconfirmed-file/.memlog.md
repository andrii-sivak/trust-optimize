- (direction) owner: spec #19 through bmad-spec before release; branch fix/gh-19-unconfirmed-file from main df37a60 (PR #46 merged); show the spec and the blocking questions; bmad-build, checks and review only after agreement; no push and no GitHub changes
- (note) issue #19: a killed worker stores relative_path on entering processing and may die before file_hash; cleanup then deletes a later file at that path because there is no hash to compare; proposal was to skip deletion when there is no file_hash and the row is not done, drop the row, leave the file
- (note) AD-13: ownership is a variant row whose relative_path the file occupies AND whose file_hash equals the file; a reservation plus a matching path is not confirmation; the plugin deletes only confirmed files; an occupied unconfirmed target is skipped with target_exists_foreign; until #19 the writer records failed/target_exists_foreign, the file is kept, and the attempt ends normally; a shared file is deleted by its last owner
- (note) AD-10 and the #30 spec: publication replaces a file only under the attempt lease; a hash proves ownership and does not close the revocation window; release and death recovery never delete a file; a first publication can leave file_hash NULL; the next attempt keeps the file and ends failed/target_exists_foreign; the file stays until an operator or #19 resolves it; death CAS does not clear relative_path or file_hash
- (note) code at df37a60: ImageCleanupService::remove_file deletes when file_hash is empty (the hash compare is skipped) after the path, uploads, protected, missing, attachment-original and shared checks; ImageConverter and AtomicImageWriter::owns_target already refuse a target with no hash; owns() is path-only; planner reconcile leaves a processing row out of delete and replaced; delete_attachment, the remove bulk, REST and WP-CLI call cleanup_attachment; uninstall calls cleanup_managed_records_batch which calls cleanup_attachment; complete uninstall depends on rows being gone (count_removable), not on the file being gone
- (note) reproduction on PHP 8.0 / WordPress 7.0, ImageCleanupServiceTest: six new tests error or fail because the file at the reserved path is deleted — cleanup_attachment (processing), wp_delete_attachment, cleanup_managed_records_batch, a done row with no hash, cleanup_variants (failed) and cleanup_replaced_files (pending, row kept). The pre-existing test test_a_row_that_reserved_its_path_but_never_finished_is_removed_with_its_file still expects that deletion. test_deleting_the_attachment_removes_variants_files_and_rows deletes a done file that has no hash and says so in a comment
- (decision) confirmation is a non-empty file_hash equal to sha256 of the file at that row's relative_path; status, including done, is not confirmation; this follows the owner direction and AD-13 and drops the issue's exception for a done row without a hash
- (decision) the fix is one guard in the existing remove_file: a missing hash skips the file with internal reason unconfirmed, a mismatch keeps reason hash_mismatch, and the row is dropped exactly when the caller already drops rows for those skips; delete_failed still keeps the row; no new service, no schema change, no change to owns(), the writer, the lease or the death CAS
- (decision) a killed worker's own unpublished file is indistinguishable from a later foreign file and stays on disk; that leftover is accepted
- (decision) explicit cleanup still drops the row while a publication lease may be set (attachment delete, remove bulk, REST, WP-CLI, uninstall); the unconfirmed file stays, so uninstall can finish and drop the tables; the planner already excludes a processing row, so no lease check is added; discard_unowned_file stays the converter's deletion of a file this request just wrote after its row is already gone
- (capability) CAP-1 cleanup deletes a generated file only when the row's file_hash matches the bytes at its relative_path; success: the six reproduction tests leave the file bytes in place, drop the row when the caller drops rows, and keep the row for replaced-file cleanup
- (capability) CAP-2 cleanup still deletes a variant whose hash matches, and still leaves originals, WordPress sizes, another attachment's original and a file shared with another variant row; success: the existing ImageCleanupServiceTest cases for those stay green, and the attachment-deletion case records a hash for the owned file it deletes
- (capability) CAP-3 a live attempt and its publication keep the #30 rules; success: the writer still refuses an unconfirmed target and does not delete it, death recovery and release still do not delete files, and the publication tests stay green with the current failed/target_exists_foreign outcome unless the open question says otherwise
- (constraint) one guard in remove_file covers cleanup_attachment, cleanup_variants, cleanup_replaced_files and the uninstall batch; callers are not given a second deletion policy
- (constraint) no schema change and no new subsystem; relative_path and file_hash stay as they are across the death CAS
- (constraint) CHANGELOG [Unreleased] Fixed records that cleanup no longer deletes a file a row cannot prove it wrote; readme is unchanged because no public hook, setting, REST route or WP-CLI contract changes
